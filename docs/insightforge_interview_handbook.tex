\section{Project Ko 60 Seconds Mein Kaise Explain Karein}

\begin{keybox}[One-line definition]
Research-Mind ek evidence-based research application hai jo recent papers aur news search karta hai, sources ko compare karta hai, cited report likhta hai, aur final report ko Critic se review karwata hai.
\end{keybox}

\subsection{Hinglish pitch}

\begin{answerbox}
``Maine tutorial ke Search Agent, Reader Agent, Writer Chain aur Critic Chain ko base rakha. Search stage OpenAlex, Google News aur optional Tavily se live sources laati hai. Reader un sources ko compare karta hai, Writer source IDs ke saath report banata hai, aur Groq Critic weak claims check karta hai. Gemini main research model hai. Maine iske upar responsive Streamlit UI, report export, follow-up Q\&A aur deployment support add kiya.''
\end{answerbox}

\subsection{English pitch}

\begin{answerbox}
``I upgraded a tutorial-based Search--Reader--Writer--Critic workflow into a usable research application. It retrieves recent scholarly and news evidence, assigns traceable source IDs, compares findings, writes a cited report, and runs an optional independent Groq review. Gemini handles the main research stages, while Streamlit provides the interface, export, and follow-up experience.''
\end{answerbox}

\subsection{Problem and users}

Search engine links deta hai, jabki normal chatbot fluent answer deta hai lekin source grounding weak ho sakti hai. Project dono ko combine karta hai.

Target users:

\begin{itemize}
  \item student jo kisi topic ka reliable overview chahta hai;
  \item researcher jo latest papers aur signals compare karna chahta hai;
  \item founder/policy professional jo trends aur limitations dono dekhna chahta hai;
  \item koi bhi person jo source-linked research brief chahta hai.
\end{itemize}

\section{Architecture and Complete Flow}

\subsection{High-level architecture}

\begin{center}
\begin{tcolorbox}[width=.72\textwidth,colback=white,colframe=Brand,arc=2mm]
\centering
\textbf{Streamlit UI}\\
$\downarrow$\\
\textbf{1. Search Agent}\\
Search plan + live source functions\\
$\downarrow$\\
\textbf{2. Reader Agent}\\
Compare every retrieved record\\
$\downarrow$\\
\textbf{3. Writer Chain}\\
Generate cited report\\
$\downarrow$\\
\textbf{4. Critic Chain}\\
Score and review completed report\\
$\downarrow$\\
\textbf{Report + Sources + Feedback + Export + Follow-up}
\end{tcolorbox}
\end{center}

\subsection{Button click ke baad exact sequence}

\begin{enumerate}
  \item User question, time range, depth, language and sources select karta hai.
  \item \code{app.py} values ko \code{run\_research\_pipeline()} mein pass karta hai.
  \item Pipeline Gemini main model aur optional Groq critic banati hai.
  \item Search Agent question ka short research plan banata hai.
  \item Question se common words remove karke search query banti hai.
  \item Selected source functions one-by-one call hote hain.
  \item Duplicate sources remove hote hain aur \code{S1}, \code{S2} IDs milti hain.
  \item Reader Agent records compare karke structured notes banata hai.
  \item Writer Chain notes + exact sources se cited report banati hai.
  \item Critic Chain completed report ko sources ke against review karti hai.
  \item Streamlit report, notes, sources, feedback and search plan tabs mein dikhata hai.
\end{enumerate}

Why sequential? Har stage ko previous stage ka output chahiye. Sequential flow beginner-friendly, traceable aur interview mein easy to draw hai.

\section{File-by-File Explanation}

\subsection{\texorpdfstring{\texttt{agents.py}}{agents.py}}

Is file mein LLM-related code hai:

\begin{itemize}
  \item \code{create\_models()} Gemini aur optional Groq banata hai;
  \item four \code{ChatPromptTemplate} objects roles define karte hain;
  \item builder functions \code{prompt | model | StrOutputParser()} return karte hain;
  \item \code{answer\_follow\_up()} collected context ke andar answer deta hai.
\end{itemize}

\begin{lstlisting}[language=Python,caption={Simple model rule}]
main_model = ChatGoogleGenerativeAI(...)

if GROQ_API_KEY:
    critic_model = ChatGroq(...)
else:
    critic_model = main_model
\end{lstlisting}

Google key required hai. Groq optional hai. Koi automatic router ya multiple fallback chain nahi hai.

\subsection{\texorpdfstring{\texttt{tools.py}}{tools.py}}

Yeh external data laata hai; LLM imagination par retrieval depend nahi karti.

\begin{tabularx}{\textwidth}{>{\bfseries}p{.25\textwidth} X}
\toprule
Function/source & Responsibility \\
\midrule
\code{search\_openalex()} & Recent scholarly papers, authors, venue, DOI, abstract and cited-by count \\
\code{search\_news()} & Google News RSS se recent reporting \\
\code{search\_tavily()} & Optional general-web results when key exists \\
\code{collect\_evidence()} & Selected sources run, errors warn, duplicates remove, IDs assign \\
\code{format\_evidence()} & Records ko model-readable text banata hai \\
\code{web\_search()} & Original tutorial-compatible wrapper \\
\code{scrape\_url()} & Original tutorial-compatible bounded URL reader \\
\bottomrule
\end{tabularx}

Each source call ka timeout hai. Ek source fail ho to warning milti hai aur next source continue hota hai.

\subsection{\texorpdfstring{\texttt{pipeline.py}}{pipeline.py}}

Yeh project ka easiest file to explain hona chahiye. Isme:

  \item \code{export\_markdown()} downloadable report banata hai.
\end{itemize}

Important state:

\begin{lstlisting}[language=Python]

Streamlit UI responsibilities:

\section{Four Stages Ko Detail Mein Explain Karein}

\subsection{1. Search Agent}

LLM pehle question ko scope karta hai: kya search karna hai, sub-questions kya hain aur blind spots kya ho sakte hain. Uske baad pipeline deterministic source functions call karti hai.

\textbf{Important honesty:} current Search Agent unrestricted autonomous tool-calling agent nahi hai. Yeh controlled prompt chain + explicit search functions ka stage hai. Isse behaviour predictable rehta hai.

\subsection{2. Reader Agent}

Original Reader ek URL read karta tha. Current Reader multiple records compare karta hai. Output mein important findings, emerging signals, disagreements aur missing evidence hota hai. Source text ko data treat karne aur embedded instructions ignore karne ka prompt hai.

\subsection{3. Writer Chain}

Reader notes aur exact source records receive karke report banati hai. Prompt ke main rules:

\begin{itemize}
  \item factual claims ke paas \code{[Sx]} citation;
  \item source/statistic invent nahi karna;
  \item weak evidence par uncertainty show karna;
  \item requested language and audience follow karna.
\end{itemize}

\subsection{4. Critic Chain}

Completed report aur sources receive karti hai. Score, strengths, improvements and verdict return karti hai. Groq available ho to independent model review milta hai; otherwise Gemini review karta hai.

Current Critic feedback report ko automatically rewrite nahi karti. Yeh visible review hai. Revision loop future improvement hai.

\section{Sources, Citations and Hallucination Control}

Har evidence record roughly yeh structure rakhta hai:

\begin{lstlisting}[language=Python]
{
    "id": "S1",
    "kind": "Academic",
    "title": "...",
    "url": "https://...",
    "published": "2026-...",
    "publisher": "...",
    "summary": "..."
}
\end{lstlisting}

Hallucination reduce karne ke methods:

\begin{itemize}
  \item live sources model context mein diye jate hain;
  \item report sirf existing \code{[Sx]} IDs cite karne ko kehti hai;
  \item temperature \code{0.15} rakha hai;
  \item snippets bounded hain, so context predictable hai;
  \item Critic unsupported/overconfident claims check karta hai;
  \item UI original source link show karti hai.
\end{itemize}

\begin{keybox}[Honest limitation]
Source ID valid hona yeh guarantee nahi karta ki source claim ko logically support bhi karta hai. Automated claim--citation entailment checker abhi nahi hai. High-stakes claims human ko original source se verify karne chahiye.
\end{keybox}

Isse vector-database RAG mat bolo. Better term: \textbf{live retrieval-augmented research pipeline}, kyunki APIs/RSS se evidence run-time par retrieve hota hai; embeddings/vector store use nahi hote.

\section{Important Decisions and Problems Solved}

\subsection{Why Gemini + Groq?}

Gemini main research flow handle karta hai. Groq optional independent Critic hai. Fixed rule automatic router se easier to understand hai. Second model correctness guarantee nahi karta, but different review perspective deta hai.

\subsection{Groq 413 request-too-large error}

Problem: report + evidence + output budget provider limit cross kar rahe the.

Simple fix:

\begin{itemize}
  \item per-source summaries 500 characters tak;
  \item Quick/Standard/Deep source limits 4/6/8;
  \item Reader, Writer and Critic inputs par direct string limits;
  \item maximum output tokens environment variable se controlled.
\end{itemize}

\subsection{PEP 668 installation error}

System Python par pip install block hua. Correct solution project virtual environment tha:

\begin{lstlisting}[language=bash]
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
streamlit run app.py
\end{lstlisting}

\subsection{Secrets and deployment}

Local development \code{.env} use karti hai. Streamlit Cloud TOML secrets use karta hai. Required/optional configuration:

\begin{lstlisting}
GOOGLE_API_KEY = "..."       # required
GOOGLE_MODEL = "gemini-3.6-flash"
GROQ_API_KEY = "..."         # optional critic
GROQ_MODEL = "openai/gpt-oss-20b"
TAVILY_API_KEY = "..."       # optional web search
MAX_OUTPUT_TOKENS = 1400
\end{lstlisting}

Real keys Git mein commit nahi honi chahiye. Exposed key ko revoke/rotate karna chahiye.

\section{Most Likely Interview Questions}

\textbf{Q1. Why multi-agent instead of one prompt?}
\begin{answerbox}
Search planning, evidence reading, report writing and quality review different responsibilities hain. Four outputs inspect kiye ja sakte hain, aur flow tutorial se naturally map hota hai. Trade-off: extra latency and model calls.
\end{answerbox}

\textbf{Q2. Are these fully autonomous agents?}
\begin{answerbox}
No. They are bounded role-based LLM stages in a controlled pipeline. Search tools explicitly Python pipeline call karti hai. I chose predictability and explainability over unrestricted autonomy.
\end{answerbox}

\textbf{Q3. Why does Reader use snippets instead of full articles?}
\begin{answerbox}
Full scraping introduces paywalls, robots rules, copyright, parsing and latency issues. Abstracts and snippets are a safe baseline. Future version official full-text/open-access APIs use kar sakti hai.
\end{answerbox}

\textbf{Q4. Why OpenAlex?}
\begin{answerbox}
It provides scholarly metadata, dates, authors, DOI links, venues, cited-by counts and many abstracts without requiring an API key.
\end{answerbox}

\textbf{Q5. Why is Tavily optional?}
\begin{answerbox}
Academic and news research should work without a paid search key. Tavily adds broader web coverage only when configured.
\end{answerbox}

\textbf{Q6. How do citations work?}
\begin{answerbox}
Collector real records ko S1, S2 IDs deta hai. Writer receives those exact records and uses IDs inline. UI/export same IDs ko source URLs se map karte hain.
\end{answerbox}

\textbf{Q7. What if a source fails?}
\begin{answerbox}
Each source call has simple error handling. Failure warning ban jati hai and remaining selected sources continue.
\end{answerbox}

\textbf{Q8. Why are calls sequential?}
\begin{answerbox}
This is a learning and interview project with only a few sources. Sequential code is easier to trace and debug. Parallel I/O can be added later if measured latency requires it.
\end{answerbox}

\textbf{Q9. Why Gemini for research and Groq for Critic?}
\begin{answerbox}
Gemini is the fixed main model and Groq gives an optional independent review. The rule is explicit and simple; I removed unnecessary automatic routing.
\end{answerbox}

\textbf{Q10. Biggest limitation?}
\begin{answerbox}
The system relies mainly on metadata/snippets and does not automatically verify that every citation entails its claim. Evidence quality and deterministic citation checking are the first improvements.
\end{answerbox}

\textbf{Q11. Why Streamlit?}
\begin{answerbox}
It lets a Python project ship forms, progress, tabs, chat and downloads quickly. For a larger multi-user product I would separate a FastAPI backend and React frontend.
\end{answerbox}

\textbf{Q12. How would you scale it?}
\begin{answerbox}
Add background jobs, persistent research sessions, caching, rate limits, authentication and async/parallel source requests. I would add these only when real usage justifies the complexity.
\end{answerbox}
